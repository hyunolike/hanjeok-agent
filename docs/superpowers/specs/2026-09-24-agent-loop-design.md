# 도구 루프

- 날짜: 2026-09-24
- 상태: 설계 확정, 구현 전
- 범위: `llm` 포트 확장, `explain` 에 `AgentLoop` 신설, `/agent/ask/stream` 이벤트 하나 추가, 하네스 대조 기준 수정

## 왜

지금 이 서비스는 요청당 모델을 정확히 한 번 부른다. 도구도 루프도 없고, 다음에 무엇을
할지는 전부 코드가 정한다. 이름은 에이전트지만 구조는 **근거가 고정된 단발 생성
파이프라인**이다.

그래서 못 하는 것이 있다. 사실 조회가 코스의 `targetDate` 와 반경 15km 로 **고정**이다.
사용자가 "다른 날은 어때요?" 나 "더 멀리 봐도 돼요" 라고 물으면 그 사실이 `facts` 에
없다. 모델은 모른다고 하거나 아는 척해야 하는데, 후자는 금지 행동이다.

## 무엇이 부딪히는가

이 서비스의 약속은 **번들에 없는 문서를 인용한 설명은 통째로 내보내지 않는다** 는 것이다.
지금 그 약속은 **근거 집합이 요청 전에 이미 확정돼 있다** 는 데 기대고 있다.

다만 ① 에 한해서는 생각보다 덜 부딪힌다. `citations` 는 **번들 문서 경로** 를 가리키고
`facts` 는 애초에 인용 대상이 아니다. 모델이 도구로 사실을 더 가져와도 인용 규칙은
건드릴 게 없다.

실제로 부딪히는 것은 셋이다.

- `AskStreamGate` 는 "출력은 한 덩어리, 검증은 한 번" 을 전제한다
- 하네스의 규칙 8종은 주장을 **초기 `facts`** 와 대조한다
- 종료 조건이 없다. 지금은 호출 1회로 끝나는 것이 구조적 보장이다

그리고 제품 쪽 긴장이 하나 더 있다. 직전 작업에서 첫 글자까지를 4.7~6.9초에서
1.1~3.5초로 당겼는데, **도구를 한 번 부르면 그 앞에 왕복이 통째로 하나 더 붙는다.**

## 결정

### 무엇을 만들고 무엇을 안 만드는가

| | 이번 | 이유 |
| --- | --- | --- |
| 질문에 따른 사실 추가 조회 | **한다** | 한적 API 가 이미 있고 스키마도 안다. 루프 기계를 여기서 세운다 |
| 인용 무효 시 수리 | **한다** | 실패 시에만 도는 1회 재시도. 평소 비용이 안 는다 |
| 번들 밖 문서 검색 | 안 한다 | 위키가 커져야 값을 한다. 검증 기준을 다시 정의해야 하는 별건 |
| 코스 변경 제안 | 안 한다 | 코스는 계속 한적이 정한다. `LLM_CHOSE` 금지는 그대로다 |
| `/agent/explain` 도구화 | 안 한다 | 첫 설명은 질문이 없어 조회할 게 없다 |

### 루프는 application 층에 명시적으로 둔다

Spring AI 의 자동 도구 호출(`ChatClient.tools(...)`)에 맡기지 않는다. 코드는 그쪽이
적지만 루프가 우리 눈에 안 보인다 — 예산을 못 걸고, 도구 인자를 검증할 수 없고,
"조회 중" 을 화면에 못 보낸다.

무엇보다 **포트가 존재하는 이유를 깨뜨린다.** 포트는 서비스 계층과 테스트 페이크를
Spring AI 없이 돌리기 위해 있는데, 도구 정의가 프레임워크 타입으로 올라오면 그 성질이
사라진다. `Flux` 를 시그니처에 올리지 않은 것과 같은 이유다.

**빠른 경로가 구조적으로 보장된다.** 모델이 도구를 안 부르면 루프는 0바퀴 돌고 지금과
같은 1회 호출 경로가 된다.

### 포트 확장

기존 `stream()` 이 쓴 수법을 그대로 쓴다 — 기본 구현을 주어 테스트 페이크 7개를
안 건드린다.

```kotlin
sealed interface Turn
data class UserTurn(val text: String) : Turn
data class ToolCallTurn(val calls: List<ToolCall>) : Turn
data class ToolResultTurn(val results: List<ToolResult>) : Turn

data class ToolCall(val id: String, val name: String, val argumentsJson: String)
data class ToolResult(val id: String, val contentJson: String)
data class ToolSpec(val name: String, val description: String, val parametersSchema: String)

sealed interface AgentStep
/** 모델이 도구를 부르려 한다. onChunk 는 한 번도 불리지 않았다. */
data class ToolRequested(val calls: List<ToolCall>, val usage: ProviderUsage) : AgentStep
/** 모델이 답했다. 조각은 onChunk 로 이미 나갔다. */
data class Spoke(val end: StreamEnd) : AgentStep

fun converse(
    systemText: String,
    turns: List<Turn>,
    tools: List<ToolSpec>,
    onChunk: (String) -> Unit,
): AgentStep
```

**`ToolRequested` 일 때 `onChunk` 는 한 번도 안 불렸다.** 이것이 계약의 핵심이다.
OpenAI 도 Anthropic 도 스트리밍에서 도구 호출과 본문을 다른 델타 타입으로 보내므로,
어댑터가 첫 델타 타입을 보고 갈라 도구 델타는 `onChunk` 에 넣지 않는다.

그 결과 **게이트의 판정 로직은 손대지 않는다.** 도구 턴은 게이트에 도달할 일이 없다.
`AskStreamGate` 에서 바뀌는 것은 아래 수리 절의 `FailureCause` 필드 하나뿐이고, 무엇을
내보낼지 정하는 규칙은 그대로다.

`ToolRequested` 를 기존 `ProviderResult` 에 넣지 않고 별도 `AgentStep` 으로 뺀 이유:
넣으면 `ExplanationService.explain()` — 도구를 주지도 않는 첫 설명 경로 — 가 있을 수
없는 경우를 처리하는 코드를 갖게 된다.

### 도구 둘

`course` 는 어차피 매 요청 받으므로 도구가 아니다.

| 도구 | 인자 | 무엇을 푸는가 |
| --- | --- | --- |
| `congestion` | `attractionId`, `date` | "다른 날은 어때요?" |
| `alternatives` | `attractionId`, `date`, `radiusKm` | "더 멀리 봐도 돼요" |

**인자는 모델을 믿지 않는다.** `AgentLoop` 가 실행 전에 검사한다.

- `attractionId` — 이 코스의 `items` 에 실재하는 id 여야 한다
- `date` — `YYYY-MM-DD` 형식이고, **코스의 `targetDate` 기준 ±14일** 안이어야 한다.
  범위를 두는 이유는 한적 예보가 그보다 먼 날짜를 갖고 있지 않아서다. 범위를 안 두면
  모델이 1년 뒤를 물어 빈 응답을 받고, 그 빈 응답을 사실로 설명하게 된다
- `radiusKm` — 1 이상 50 이하. 기본 15 는 그대로 두고 모델이 넓힐 때만 쓴다

**검사에 걸리면 예외를 던지지 않고 도구 결과 자리에 거부 사유를 넣어 되먹인다.**
모델이 그걸 읽고 고쳐 부르거나 포기할 수 있어야 한다. 던지면 한 번 잘못 부른 것이
요청 전체를 죽인다.

### 예산과 종료

| | 값 | 왜 |
| --- | --- | --- |
| 도구 라운드 | 최대 2 (모델 호출 ≤3회) | 도구가 둘뿐이라 2라운드면 둘 다 부르고 남는다 |
| 마감 | 루프 시작부터 60초 | emitter 가 90초다. `aborted` 라도 낼 여유를 둔다 |
| 수리 | 1회, 도구 라운드와 별개 | 마감 60초는 공유한다 |
| 모르는 도구 | 거부 결과 되먹임 | 실패가 아니다 |

**예산이 떨어지면 실패가 아니라 "가진 걸로 답하라" 다.** 마지막 호출은 **도구를 아예
빼고** 보낸다. 모델이 다시 부르는 것이 구조적으로 불가능해진다 — 잘못 쓸 자리를
없애는 편이 검사를 더 다는 것보다 낫다(base URL 때와 같은 수법).

### 프롬프트 캐시에 미치는 영향

Anthropic 의 캐시 접두사는 `tools → system → messages` 순이다. 도구를 실으면 접두사가
바뀐다. 도구 정의는 요청마다 같으므로 배포 후 한 번만 깨지고 이후엔 유지되지만,
**경로별로 접두사가 갈린다:**

- 도구 있는 라운드
- 도구 없는 경우 — `/agent/explain`, 그리고 예산 소진 후 마지막 라운드

캐시 항목이 1개에서 2개가 된다. 각 접두사의 첫 요청에서 22KB 를 한 번 더 계산하는
비용이고 그 뒤로는 평소와 같다.

**도구 사용 지침은 `system` 이 아니라 user 턴에 넣는다.** `system` 은 번들 원문
그대로여야 한다.

### 이벤트 하나 추가

| 이벤트 | 언제 | 내용 |
| --- | --- | --- |
| `looking` | 도구를 **실행하기 직전** | `{"what":"congestion"}` 또는 `{"what":"alternatives"}` |

도구 이름만 보낸다. 인자(관광지 id, 날짜)는 싣지 않는다 — 실패 이벤트가 사유를 싣지
않는 것과 같은 선이다. 화면에 보일 문구는 프론트가 정한다.

**도구 호출 하나당 하나씩 보낸다.** 모델이 한 턴에 둘을 부르면 `looking` 도 둘이다.
인자 검증에 걸려 실행하지 않은 호출은 보내지 않는다 — 사용자에게 "조회 중" 이라고
말해 놓고 조회하지 않는 상태를 만들지 않는다.

**기존 불변식은 그대로다.**

- `looking` 은 `delta` 가 아니다 → **"`unavailable` 이 오면 앞의 `delta` 는 0개" 가
  여전히 참이다.** `looking` 몇 개 뒤에 `unavailable` 이 오는 것은 정상이다
- 도구 요청 턴은 `onChunk` 를 부르지 않는다 → 게이트에 도달하지 않는다
- 검증을 통과하지 않은 글자는 한 자도 나가지 않는다 → 손대지 않았다

### 텍스트와 도구가 한 턴에 섞이는 경우

Anthropic 은 한 턴에 텍스트 블록과 도구 블록을 둘 다 낼 수 있다.

**규칙: 본문이 이미 나가기 시작했으면 그 턴은 최종 답으로 친다. 같은 턴의 도구 호출은
무시한다.**

안전 문제는 없다 — 나간 본문은 게이트가 인용을 검증한 것이다. 답의 질이 조금 나빠질
수 있을 뿐이다. 반대로 하면(중간에 끊고 도구를 부르면) 사용자가 읽던 문장이 사라진다.
빈도는 user 턴 지침("필요한 사실이 없으면 **먼저** 도구를 부르고 그다음에 답하라")으로
줄인다.

### 수리 루프

여기 좋은 성질이 있다. **인용 무효로 실패하면 `delta` 가 반드시 0개다** — 게이트가
보장하는 그 불변식이다. 즉 인용이 틀려서 실패한 시점에 사용자는 **아직 한 글자도 못
봤다.**

그래서 스트리밍을 버퍼링하지 않고도 수리할 수 있다.

```
1차 → 게이트가 citations/delta/done 을 그대로 흘려보냄
       └ unavailable(인용 무효) → 그 이벤트 하나만 삼키고 재시도
2차 → 정상이면 그대로 흘림, 또 무효면 진짜 unavailable
```

사용자가 보는 것은 조금 길어진 대기 하나뿐이다.

**무엇에 대해서만 수리하는가.** 거절이나 스트림 실패는 다시 해도 같다. 인용 무효일
때만 돈다. 지금 `UnavailableEvent` 는 사유가 문자열인데, **이것을 문자열로 판별하지
않는다** — 이 저장소는 이미 문자열 분류로 데인 적이 있다. 타입을 붙인다.

```kotlin
enum class FailureCause { INVALID_CITATIONS, REFUSED, STREAM_FAILED, EMPTY, TRUNCATED, FACTS }
data class UnavailableEvent(val reason: String, val cause: FailureCause) : AskStreamEvent
```

`INVALID_CITATIONS` 만 수리를 부른다.

수리 턴은 무효였던 경로를 돌려주며 다시 쓰게 한다. 번들 경로 목록은 이미 `system` 에
`----- FILE: -----` 마커로 전부 들어 있으므로 따로 싣지 않는다.

**수리 턴에는 도구를 싣지 않는다.** 인용이 틀린 것은 사실이 모자라서가 아니라 경로를
잘못 적어서다. 도구를 주면 모델이 조회를 한 번 더 돌 여지가 생기고, 그만큼 마감 60초를
까먹는다. 도구 없는 마지막 라운드와 같은 접두사를 쓰므로 캐시 항목도 안 는다.

### 하네스

**하네스가 루프를 안 돌면 하네스가 낸 숫자는 배포된 것에 대해 아무 말도 하지 않는다.**
이 프로젝트가 이미 한 번 저지른 실수다 — 측정은 OpenAI 로 하고 서버는 Anthropic 으로
돌던 때, "위반율 0%" 는 도는 서버에 대한 문장이 아니었다. `EvalMain` 이 루프를 타게
하고 도구는 같은 픽스처로 받친다.

**규칙 8종의 대조 기준을 고친다.** 지금 `UNCITED_CLAIM` 같은 규칙은 주장 문장을 **초기
`facts`** 와 대조한다. 도구로 가져온 사실은 거기 없다. 그대로 두면 **도구가 가져온
사실을 말할 때마다 근거 없는 주장으로 잡힌다** — 도구를 붙이는 순간 위반율이 치솟는데
그것은 모델이 나빠진 것이 아니라 판정기가 못 따라간 것이다.

대조 대상을 **초기 facts + 실행된 도구 결과 전체의 합집합** 으로 바꾼다. 합집합은
`FactsNormalizer` 가 만든다 — 도구 결과를 초기 facts 와 같은 투영 모양으로 정규화해
한 JSON 트리에 합친다. 거부된 도구 호출의 결과는 합집합에 넣지 않는다. 실행되지 않은
조회가 근거로 잡히면 안 된다.

새로 재는 것: 도구 호출 횟수 분포, 예산 소진률, 수리 발동률과 성공률.

## 테스트

`CapturingEndpoint` 를 확장해 **미리 짠 도구 호출 스트림** 을 돌려주게 한다. 키도
네트워크도 없이 루프 전체가 결정론적으로 돈다.

| 입력 | 기대 |
| --- | --- |
| 도구 요청 → 실행 → 답변 | `looking` 뒤 `citations`, `delta` 들, `done` |
| 모델이 계속 도구만 요청 | 모델 호출 정확히 3회, **마지막 요청에 도구가 실려 있지 않다** |
| 없는 `attractionId` | 예외가 아니라 거부 사유가 도구 결과로 되먹여진다 |
| 범위 밖 `date`, 상한 초과 `radiusKm` | 같음 — 거부 사유 되먹임 |
| 텍스트 뒤 도구 블록 | 최종 답으로 처리, 도구 호출 무시 |
| 1차 인용 무효 → 2차 유효 | 사용자에게 `unavailable` 이 **한 번도 안 간다** |
| 거절 | 수리하지 않고 바로 `unavailable` |
| 마감 60초 초과 | 도구 없는 마지막 호출로 넘어간다 |
| 도구 라운드를 거친 뒤 인용 무효 | `delta` 0개 — 인용 먼저·본문 먼저 양쪽 |

마지막 줄이 핵심이다. 기존 안전 테스트가 루프를 거친 뒤에도 성립하는지를 본다.

도구가 실린 요청 본문이 실제로 `tools` 필드를 싣는지, 그리고 마지막 라운드가 그것을
싣지 않는지도 루프백 캡처로 고정한다.
